# 開發流程本體（由全域 CLAUDE.md 的 Q1 路由後載入）

前置：Q1（驗收基準）與 Q2（執行者模型）已在全域 CLAUDE.md 答完。本 skill 只提供各支的執行細節。

## TDD 流程（Q1 第 2 支）

0. 測試可由既有工具生成（spec-driven codegen）時，跑生成指令並對未實作骨架跑一次確認 red，即視為第 1 步完成；恆綠 = 生成缺陷。
1. 派 **Opus** 分析需求並寫測試。briefing 必含：「寫完後**在同一個 agent 內跑一次**，回報必須附上 `N failed` 的原始輸出；若全綠，先確認功能是否已存在——已存在就停下回報，否則測試無效、重寫」。red 是機械事實，不另派 agent 確認。
   主 agent 收到回報後：(a) **讀一遍測試檔**確認斷言對應需求（red 檢查抓不到「測試寫錯規格」，這是唯一守門）；(b) `git add <測試檔>` 固定基準，再進第 2 步。
2. 派 **Sonnet** 實作到測試轉綠。briefing 必含：(a)「動手前先跑測試，若已全綠立刻停下回報，不要改碼」；(b)「測試檔唯讀，不得修改、跳過或放寬斷言；卡住就回報，不要繞過」；(c)「同一個失敗修兩輪仍不綠 → 停下回報卡在哪」。Sonnet 回報卡住 → 升級派 Opus 收尾或交使用者，不再派第二個 Sonnet。
3. 主 agent 自己跑測試判定綠；`git diff -- <測試檔>` 必須為空（工作樹相對 index 無改動）；掃一眼實作 diff（有無 hardcode 湊答案、改動範圍有無溢出）。不為空 → Sonnet 越權，依全域 CLAUDE.md〈驗證鐵律〉的 sub agent 越權條處理（還原測試檔重跑、換人重派）。

   **例外——主 agent 發現測試本身有誤**：可以修，但真正要守的是「寫測試的人 ≠ 讓它綠的人」，不是「測試檔沒有 diff」。所以修完必須：(a) 重新 `git add` 固定新基準；(b) 重新確認 red；(c) **實作要跟著改就派回 Sonnet，主 agent 不得自己改**。修改理由寫進回報。此例外只給主 agent，「測試檔唯讀」對 sub agent 無例外。
   分辨兩種情形：斷言意圖錯（誤解規格）→ 實作可能已被帶歪，(a)(b)(c) 全走；純 fixture 技術瑕疵（例如 `new Date(2026,1,30)` 溢出成 3/2，斷言意圖其實正確）→ 修好後若實作不需動，主 agent 自己重跑判綠即可。

註：bug fix 若既有測試未覆蓋，「寫 failing test」本身就是 root-cause 的大半，屬第 1 步；既有測試已 red 則走 Q1 第 1 支。

## UI 視覺比對流程（Q1 第 3 支）

前提：使用者提供設計圖／目標截圖；瀏覽器操作用 Claude in Chrome MCP（`mcp__claude-in-chrome__*`），dev server 已在跑。「一組截圖」＝ 一個狀態的設計圖 1 張 ＋ 實作截圖 1 張。

1. 主 agent briefing 附上設計圖路徑、頁面 URL，並**明列設計圖未涵蓋但要做的狀態**（hover / error / loading / empty / responsive 斷點）；未列的狀態依專案 design system 慣例，找不到慣例就回報主 agent 詢問，不自行選定。
2. 派 **Sonnet** 實作，迴圈內用 Claude in Chrome MCP 截圖對照設計圖自行修正，每個列出的狀態各截一張；最多 4 輪，第 4 輪仍有差距 → 停下回報差在哪，不要繼續猜。判定標準是「版面／間距／色彩／字級符合設計意圖」，**不做 pixel diff**（字型抗鋸齒必差）。回報截圖時的 URL 與操作步驟。
3. 主 agent 自己用 Claude in Chrome MCP 開同一頁截圖，對照設計圖定案；≤4 組自判，組數更多或看了不確定，才派**一次** Opus 驗證者看全部截圖。
4. 同任務的行為邏輯測試（Q1 第 2 支）：**非瀏覽器層**（unit / component）可與第 2 步平行派 Opus 寫；**瀏覽器驅動**（Playwright / e2e）的測試排在第 3 步定案後序列進行，不與截圖迴圈搶瀏覽器。

Claude in Chrome MCP 是使用者的同一個瀏覽器：**需要瀏覽器的 sub agent 一次只派一個**（其他類型任務可照常平行）；briefing 規定用 `tabs_create_mcp` 開新 tab、結束 `tabs_close_mcp`、不碰使用者既有 tab。

## 執行 → 驗證 → 修正 循環（Q1 第 4 支且 diff 超過主 agent 自審門檻）

1. **派執行** → 交付物回報主 agent。
2. **派驗證（第 1 次）**：新開一個 `subagent_type: "general-purpose"`、`model: "opus"` 當驗證者，給它**明確的驗收標準**（要重跑哪些指令、核對哪些檔案/diff/log、什麼叫通過）。**執行者與驗證者必為兩個不同的 sub agent**——驗證的價值來自獨立性，自我驗證有盲點。
3. **驗證者回傳**：`通過 / 不通過` + 佐證（指令輸出、diff、關鍵檔案內容）；不通過要指出**哪裡錯、怎麼錯**。
4. **不通過 → 派執行修正**：把驗證者的失敗發現 briefing 給執行 sub agent。
5. **驗證（第 2 次）**：只需確認「指出的點有沒有修掉」→ `SendMessage` 回第 1 次的驗證者複查；要重新做品質判斷 → 開新的 fresh Opus（避免錨定第一輪結論）。這次判定直接決定是否升級給人。
6. **第 2 次仍不通過 → 停止循環，交給使用者**。不可無限重試；把兩輪累積的證據（改了什麼、為何仍失敗、卡在哪）整理後請使用者判斷。

這一支同樣受全域 CLAUDE.md〈驗證鐵律〉約束（主 agent 保有最終權威、驗證者說通過仍要便宜複核）——那段常駐，不在此重複。

## 補救驗證（主 agent 自己實作、或 sub agent 越權後，產物要保留時）

前置：全域 CLAUDE.md 的〈主 agent 自己動手之後〉或〈驗證鐵律〉的 sub agent 越權條已判定「要派驗證者或要補測試」。本節只補「怎麼把獨立性事後補回來」；驗證者回傳格式、不通過派修正、第 2 次仍不過升級給人，沿用〈執行 → 驗證 → 修正 循環〉第 3–6 步，不重複。第 4 步的「執行 sub agent」在補救情境下不存在（執行者是主 agent），新派一個，模型依 Q2 選。

### 驗證者 briefing：該給／不該給

**該給（全部）：**

1. 任務原文（使用者逐字，不摘要）。
2. 驗收標準：要跑哪些指令、核對哪些檔案、什麼叫通過（沿用 Q1 原本那一支）。
3. 改動座標：檔案清單 ＋ base sha ＋「用 `git diff <base>..HEAD` 自己讀」的指令。給指令，不給摘要過的 diff。
4. 專案跑測試／lint 的指令。
5. **明講「這份改動未經獨立驗證，這是補救驗證」**，並說明誰寫的（主 agent 自己／越權的 sub agent，測試與實作是否同一作者）。隱瞞會讓驗證者以為只是複查而降低警覺。
6. 優先找的三件事：為讓測試綠而取巧（hardcode、特判 fixture 值）、測試盲點（需求中未被斷言的行為）、改動範圍溢出。
7. 不通過要指出哪裡錯、怎麼錯。

**不該給：**

1. 主 agent 對自己改動的正確性主張（「我確認這樣是對的因為…」）。
2. 設計理由辯護。真有非顯而易見的取捨，改寫成中性問句：「X 與 Y 兩種作法，現況選了 X，請判斷是否合理」。
3. 任何人先前說過的「看起來沒問題」。
4. 「這個任務很簡單」「改動很小」這類降低警覺的描述。
5. 主 agent 自己猜的可疑點——驗證者會只查那幾點，放過其他。

### 事後 TDD（Q1 第 2 支的產物已存在）

Opus 驗證者只能讀 diff 做人類式判斷，比機械測試弱一個檔次；第 2 支的補救是**補測試**，不是補驗證者。派 **Opus** 寫測試，briefing 範本：

> 功能已由 `<誰>` 實作在 `<檔案清單／commit sha>`。請從下列任務原文寫測試：`<逐字原文>`。⚠️ 不要因為「功能已存在」停下回報——本次就是已存在的情況。寫完後在同一個 agent 內做兩件事並附**原始輸出**：(1) 現況跑一次，必須全綠；(2) 挑實作中對應本需求的**關鍵那一行**做單點破壞（反轉條件／改常數／換 return 值），再跑一次，必須 red。⚠️ 破壞前先 `cp <該檔> /tmp/<basename>.bak`，破壞後用 `cp /tmp/<basename>.bak <該檔>` 還原，**不要用 `git checkout --`**——實作若尚未 commit，那會把實作一起還原掉。還原後再跑一次測試確認回到全綠，附上輸出。回報你破壞了哪一行、為什麼那一行是關鍵。若破壞後仍全綠 → 你的測試沒測到這個行為，重寫。

主 agent 收到後照 TDD 第 1 步 (a)(b)：讀測試檔確認斷言對應需求、`git add` 固定基準。現況不綠 → 派 Sonnet 修，主 agent 不得自己改。Opus 回報重寫一次後單點破壞仍全綠 → 停下，多半是這個需求無法機械斷言，退回 Q1 第 4 支走人類式判斷驗證，不要再派第三輪。

- **不用 `git stash` 在 base 上確認 red**：需要精確列出實作檔（auto 模式 heredoc 改檔後常說不清），漏一個就是假 red；pop 還會衝突。單點破壞更便宜，且直接抓「斷言太弱」這個 red-on-base 抓不到的高頻錯。
- red-on-base 只在「改動已 commit **且** 單點破壞不好定位（例如刪掉一整段邏輯）」時做：`git worktree add <tmp> <base sha>`，把測試檔複製過去跑。

### 兩個角色都被同一人做掉（實作先有、測試後補）

限定：測試是在實作已存在的情況下寫的。若是「寫測試的 sub agent 順手寫了實作」（測試先寫且回報過 red），測試仍可信，依全域 CLAUDE.md〈驗證鐵律〉的 sub agent 越權條處理，不適用本節。

測試會順著實作的形狀寫，必然綠，單派驗證者會被「測試綠了」騙過。處理：**測試檔作廢重寫**，派 Opus，briefing **只給任務原文，不給現有測試檔**（防錨定），照上面的事後 TDD 範本走。新測試在現有實作上 red → 證明原測試在遷就實作，實作也派出去重做。

### 違規點回溯

違規產物已被後續工作依賴（主 agent 自己實作了 A，再派 sub agent 基於 A 做了 B）時，驗證範圍從**最早的違規點**起算（A＋B），不是只看最後一個 commit；A 不通過，B 連帶重做。
