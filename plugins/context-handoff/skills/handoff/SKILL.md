# Handoff Skill（session 交接：把進度寫進記憶）

## 這個 skill 在做什麼 / 為什麼

使用者準備要 `/clear` 或開新 session，但目前對話裡有正在進行的任務。一旦清空，這些「做到哪、為什麼這樣決定、下一步是什麼」的 context 就沒了。這個 skill 的職責是：**在清空前，把足以讓一個全新 session 接手的資訊，沉澱進專案的長期記憶**。

心智模型：你寫的不是給自己看的暫存，而是給「一個完全沒有這段對話、只讀得到記憶檔的新 Claude」看的接班交接書。判準只有一個 —— **新 session 只讀這份記憶，不看對話歷史，能不能正確接續？** 缺了哪個檔案路徑、哪個指令、哪個決策原因會讓他卡住，就得補進去。

重要邊界：**這個 skill 不會、也無法自己 `/clear`**。清空是使用者的動作。你的交付物是「記憶已寫好、已確認可安全清空」；寫完後明確告訴使用者可以清了。

## 前置：定位記憶目錄

專案記憶存在該專案的記憶目錄，索引檔是 `MEMORY.md`。此路徑會出現在你的 session context（記憶系統說明）裡，形如：
`/Users/<user>/.claude/projects/<專案 slug>/memory/`

先讀該目錄的 `MEMORY.md` 索引，掌握現有記憶清單。若 context 裡找不到路徑，用 `ls` 從 `~/.claude/projects/` 依當前工作目錄推出對應的專案 slug（工作目錄的絕對路徑把 `/` 換成 `-`）。

## Step 1：盤點當前 context

回看這整段對話，抽取出交接所需的要素。**只寫確實發生過的事，不要臆測或美化進度**：

- **任務目標**：現在在做的這件事，一句話講清楚「要達成什麼」。
- **已完成**：具體做了什麼（改了哪些檔、跑了哪些指令、合了哪個 commit/MR）。用 `✅` 標記，附絕對日期。
- **進行中／下一步**：接手的人第一件該做的事是什麼，越具體越好（要改哪個檔的哪個函式、要跑哪個指令）。
- **關鍵決策與其原因**：為什麼選 A 不選 B。這是對話裡最容易蒸發、也最貴的東西 —— 沒有它，新 session 會重踩一次坑或推翻既有決定。
- **踩過的坑 / gotcha**：試過但行不通的路、容易記錯的 API 位置、環境雷點。
- **阻塞**：卡在什麼、在等什麼（等後端、等 review、等某個前置）。
- **相關檔案／指令／連結**：接手需要的路徑、指令、MR/issue 連結。

若一個 session 同時推進了多個獨立任務，分別盤點、分別對應到各自的記憶（見 Step 2）。聚焦真正「進行中、需要接續」的任務；已經徹底收尾、無後續的事不必為了交接硬寫。

## Step 2：去重 —— 找出對應的既有記憶（優先更新，不亂開新檔）

**這是本 skill 的硬性要求**：重複執行 handoff 時，絕不能每次都新開一個檔堆疊重複內容。做法：

1. 從 `MEMORY.md` 索引比對：目前這個任務，是否已有一則 `type: project` 記憶在追蹤它（例如某個遷移計畫、某個升級任務、某輪清理）？用任務主題比對，不要只看檔名字面。
2. **有對應記憶 → 讀完整檔內容**，判斷這次的新進度是否已經被記錄過：
   - 有實質新進展（新完成項、決策更新、下一步改變、坑點修正）→ **就地更新那個檔**：補新段落、把過期敘述改對、狀態標記從進行中改 `✅`。保留仍有效的歷史，只修正／追加，不要整檔重寫掉有用的脈絡。
   - 若內容與記憶中已有的完全一致、這次沒有任何新東西 → **不要寫**，直接告訴使用者「目前進度記憶中已是最新，無需更新」。
3. **找不到對應記憶 → 新建一個** `type: project` 記憶檔（kebab-case 檔名，貼合任務主題）。

## Step 3：寫入／更新記憶檔

遵循此專案既有記憶格式（可打開同目錄任一 `project-*.md` 對齊）：

```markdown
---
name: <kebab-case-slug，與檔名一致>
description: <一行摘要，用於日後 recall 時判斷相關性>
metadata:
  node_type: memory
  type: project
---

# <任務標題> <進行中／✅ 已完成 之類的狀態>（<絕對日期>）

## 任務目標
...

## 已完成（截至 <絕對日期>）
- ✅ ...

## 進行中 / 下一步
- 接手第一步：...

## 關鍵決策
- 選了 X 而非 Y，因為 ...

## 踩過的坑 / 注意
- ...

## 阻塞
- ...（沒有就省略此段）

## 相關檔案 / 指令 / 連結
- `lib/...`
- MR !NN / issue #NN

[[相關記憶的 name]]
```

寫入規則：
- **日期一律絕對**（`2026-07-13`），不要寫「今天／昨天／三天前」—— 記憶會被跨時間讀取，相對日期會失真。今天日期見 session context 的 currentDate。
- 用 `[[name]]` 連結到相關的既有記憶（例如同專案的架構、前置需求、相鄰任務），讓脈絡串起來。連到還不存在的 name 也沒關係，那代表日後值得補。
- 資訊密度優先於篇幅，但**寧可多寫一個接手需要的檔案路徑或指令，也不要為了精簡把它省掉**。此 skill 的交付物本質就是「可續作性」。
- 別把 repo 本身已記錄的東西（程式碼結構、git 歷史、CLAUDE.md 已寫的）搬進來；記憶只放「光看程式碼／git 推不出來」的決策與進度。

## Step 4：更新 MEMORY.md 索引

- 新建記憶 → 在 `MEMORY.md` 加一行指標：`- [標題](檔名.md) — 一句話 hook`。
- 更新既有記憶 → 若該行的 hook 已不能反映最新狀態（例如從「進行中」變「已完成」、或下一步變了），順手改這行；否則不動。

## Step 5：回報並確認可安全清空

寫完後，給使用者一段簡短收尾：
- 這次**寫入還是更新**了哪個記憶檔（給檔名）。
- 一句話摘要交接了什麼、新 session 接手的第一步是什麼。
- 明確一句：**「進度已存入記憶，可以安全 `/clear` 或開新 session；新 session 讀 MEMORY.md 即可接續。」**
- 若 Step 2 判定無需更新，也要講清楚「已確認記憶是最新、無需重寫，可直接清空」。

## 快速範例

**使用者輸入**：`handoff`

**流程**：讀 `MEMORY.md` → 發現目前在推進的「套件升級」對應到既有 `project-painless-package-upgrade.md` → 讀完整檔 → 這次多完成了兩個套件、且下一步改變 → 就地更新該檔的「已完成」與「下一步」、狀態日期更新 → MEMORY.md 那行 hook 微調 → 回報：「已更新 `project-painless-package-upgrade.md`（新增 device_info_plus / secure_storage 已升完，下一步為階段 B 的 breaking 套件）。進度已存入記憶，可安全 /clear。」
